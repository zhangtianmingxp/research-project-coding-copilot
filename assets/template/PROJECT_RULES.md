# 项目规则

## 1. 项目定位

本项目不是 demo，不是一次性脚本集合，也不是只为了跑通一个模型的临时实验。

本项目定位为正式、长期、可迭代、可发表论文或支撑高质量科研结论的研究代码项目。所有代码、实验、文档和结果都必须服务于以下目标：

- 可复现；
- 可扩展；
- 可解释；
- 可比较；
- 可审稿；
- 可长期维护；
- 可支撑论文发表或严肃科研交付。

### 1.1 主线优先与宽度优先推进

项目的优化目标是回答核心科学问题并形成可信、重要、连贯的论文证据链，不是把仓库打磨成工程功能最齐全的软件。

本节是后续通用工程建议的优先级解释规则。若某项模块化、测试、文档、接口或维护建议会推迟当前有效模型实验，且它并不影响数据有效性、泄漏、指标或核心结论，则该建议不是本阶段的前置条件。

- 每一轮工作都应说明它推进哪个核心 claim、关键不确定性、figure/table 或明确 blocker；
- 每轮重新比较数据、基线、候选模型、实验、分析和工程行动的信息增益，不因某个子任务尚未完成就默认继续深挖；
- 一旦数据足以定义有效 target、split 和 metric，应尽快形成简单基线、候选模型和科研决策级比较；
- 工程化只做到足以保障正确性、可复现性、数据完整性和论文关键分析；
- 已经跑通的代码路径不得因为“更稳妥”而反复做同级小样本验证；
- contract、schema、重构、文档和额外测试若不影响主线结果，不应连续占用正式轮次；
- 一个工程 blocker 先给一次聚焦修复机会；仍未解决时优先绕过、简化、换实现或判为 INCONCLUSIVE。不得连续两轮只做工程补强，除非它会使核心证据失效且没有科学上有效的替代路径。

如果目标参照 CNS 或高水平子刊，应优先考虑：概念新颖性、科学重要性、机制深度、严格统计、稳健性、泛化能力、外部或正交验证，以及清晰的 claim-to-figure 故事。工程复杂度本身不是论文贡献，也不能保证投稿结果。

发现问题后先按主线影响分级：

- **claim blocker**：可能改变数据有效性、泄漏判断、指标、统计推断、核心图表或关键结果复现，必须优先解决；
- **重要但不阻断**：有助于稳健性、维护或审稿回复，但不推翻当前结论，进入待办并按论文优先级安排；
- **偶发或无关问题**：外观、推测性、极少见且不能影响核心证据，只需简要记录，不得为它反复实验或单独占用正式轮次。

### 1.2 项目组合与成果收割 Gate

启动任何后继版本前，应对明确项目组合范围内的所有项目族做一次轻量、只读的成果收割审计。按同一数据、outcome 和核心问题合并版本，去除镜像、模板和改名副本；优先读取 `paper_map.md`、投稿/稿件决定、checkpoint 和终局 result，不展开全部历史。

每个项目族先定义一个最小可发表单元，再且只分到一个资源动作：

- `WRITE_NOW`：已有边界清楚、无致命有效性缺口的最低可发表证据，并且对至少一个现实投稿层级有可辩护贡献。冻结新模型、新实验和后继版本，完成稿件、图表、方法、局限、复现材料与投稿；高目标期刊不得阻断一个成立的边界清楚论文；
- `ONE_DECISIVE_EXPERIMENT`：只缺一个明确、可行、达到决策级规模且能把投稿判断改为 WRITE_NOW 或关闭/降级项目族的比较。只运行这一个实验，最多 1-3 轮，然后重新分类；
- `HOLD`：仍可能有价值，但存在多个实质缺口、依赖暂不可得资源，或当前组合价值较低。外部条件或资源优先级改变前不生成 prompt 或新版本；
- `STOP`：当前数据和问题下存在致命有效性、创新性、可识别性或可行性障碍，关闭项目族但保留证据。

上述标签是项目组合资源决策，不替代单轮 `GO / PIVOT / STOP / INCONCLUSIVE`。默认只在对话中输出一张紧凑分类表，不新建 registry；证据仍只维护在现有 `paper_map.md`。证据不足以支持其他分类时使用 HOLD，并明确缺失事实和有限置信度。

### 1.3 跨版本项目族止损

复用同一数据、outcome 和核心科学问题的多个版本属于同一项目族。版本号变化不等于获得新证据，不得通过更换版本名持续重启已失败的路线。

- 启动后继版本前，先有界读取前序版本的终局 result、checkpoint、计划书摘要和 `paper_map.md`，提取导致 STOP 的根本 blocker；
- 新版本必须引入能够检验或解除 blocker 的新信息，例如独立数据/生物学单位、更高测量分辨率、真正不同且避开原限制的 estimand、外部/正交证据，或在查看失败结果前已有独立支持的假设；
- 仅更换模型、特征编码、阈值、seed、metric、亚组、post-hoc label 或版本号，不足以重启。亚组或替代 outcome 必须有独立先验依据，并能与事后挽救解释区分；
- 同一根本 blocker 已导致两个版本 STOP 时，默认关闭该 claim/数据项目族，除非新证据直接解除 blocker；同一数据/outcome 项目族连续三个版本 STOP 后，任何重启前必须做项目族审计；
- 审计只给 `GO / PIVOT / STOP / INCONCLUSIVE`：只有 GO 可以建立新版本；PIVOT 要求更换数据或科学问题；STOP 关闭项目族；INCONCLUSIVE 只指出一个决定审计所需的外部事实；
- STOP 后最多做一次聚焦失败归因，只用于确认根本 blocker 和判断是否存在独立动机的新假设，不得用它挽救已关闭 claim，也不得递归开展 post-hoc 审计。

上述次数是研究组合管理的默认止损线，不是统计学阈值。只有用户明确要求，并在现有 `paper_map.md` 中记录新增证据和覆盖理由时才可例外；不得新建版本 registry。

### 1.4 短活动计划

`project_plan.md` 只详细展开当前活动 Gate：claim、决定性比较、最低决策级规模、判据、产物和立即分支。未解锁的后续 Gate 各用一句话记录，只有上游结果 GO 后才展开。不得提前写出远期 Prompt5-Prompt11 的完整任务树。

计划书建议不超过约 300 个非空行或 20 KB；这只是低上下文提醒，不会替代科学判断或阻断有效长计划。已有长计划应明确一个紧凑的“当前活动 Gate”，AI 默认只读取该段及必要全局章节。

## 2. 总体工程原则

### 2.1 不写一次性核心代码

探索阶段允许用清晰、可追踪的单脚本或 notebook 尽快完成首次有效模型比较。此时只需记录输入、参数、随机种子、命令和输出，不得为了未来复用提前建设通用框架。

只有路线获得 GO、需要重复运行或准备升级为 paper-grade 时，才把稳定逻辑沉淀到模块化源码并消除硬编码。

### 2.2 模块之间低耦合、少依赖

对已经进入重复使用或 paper-grade 的核心流程，模块设计应遵循低耦合原则：

- 数据读取模块不依赖模型训练模块；
- 特征构建模块不依赖具体模型；
- 模型模块不依赖具体数据文件路径；
- 评价模块不依赖某个特定模型实现；
- 可解释性模块可以读取模型输出，但不应反向污染训练逻辑。

每个模块应该有清晰输入、清晰输出和清晰责任边界。

### 2.3 可替换、可扩展

后续可能新增模型、数据集、特征、评价方式和组学模态，因此所有设计都要方便替换：

- 可以替换数据集；
- 可以替换特征构建策略；
- 可以替换模型；
- 可以替换训练配置；
- 可以替换评价指标；
- 可以新增数据模态或实验任务。

如果某个设计会让后续替换变得困难，优先重新设计。

上述要求只应用于当前或可预见的论文关键流程。不得为假设性的未来需求提前制造抽象层、全面重构或扩大测试范围。

### 2.4 代码成熟度跟随证据成熟度

不得在科学路线尚未得到支持时投入全面工程化。代码要求分三档：

1. **探索阶段**：最短可读实现、固定随机种子、记录命令和输出，重点是尽快判断方向；
2. **决策级阶段**：可复现命令、必要配置、数据有效性与泄漏检查、正确指标；
3. **论文级阶段**：再补模块边界、系统测试、日志、错误处理、文档和长期维护能力。

以下要求主要适用于进入重复使用或论文级的核心路径：

- 函数职责单一；
- 类和模块命名清楚；
- 配置与代码分离；
- 数据路径不硬编码；
- 日志完整；
- 随机种子可控；
- 实验结果可追踪；
- 错误信息清楚；
- 关键流程有测试或校验。

## 3. 推荐代码组织

推荐结构：

```text
project/
├── configs/                 # 实验配置
├── data/                    # 本地数据入口，原则上不提交大文件
│   ├── raw/
│   ├── external/
│   ├── interim/
│   ├── processed/
│   └── metadata/
├── docs/                    # 文档、计划书、方法说明
├── notebooks/               # 探索性分析
├── results/                 # 结果输出，原则上不提交大文件

```

如果采用其他结构，也必须保证职责边界清楚。

## 4. 数据规则

### 4.1 原始数据不可随意修改

原始数据必须保持只读。任何清洗、过滤、标准化和格式转换都应输出到新的中间文件或结果目录。

### 4.2 数据处理必须可追踪

每个 processed 数据都必须能够追踪来源：

- 来自哪个 raw 文件；
- 使用了哪个脚本；
- 使用了哪个配置；
- 生成时间；
- 过滤标准；
- 归一化方法；
- genome version、annotation version 或领域内等价版本信息。

### 4.3 严格避免数据泄漏

预测任务必须特别注意数据泄漏。根据任务类型，至少考虑：

- random split；
- sample / cell / patient holdout；
- feature / gene / target holdout；
- chromosome / region / group holdout；
- condition / time / batch holdout；
- tissue / cell line / cohort holdout。

论文主结果或核心结论不能只依赖最宽松的 random split。

## 5. 实验规则

### 5.1 配置要求随证据阶段升级

探索性首次比较可以使用一个清晰脚本、命令行参数或小型配置，只要实际参数和命令被记录。科研决策级与论文级实验才要求模型、数据、特征、训练参数和评价方式系统配置化。

配置中至少包含：

- dataset；
- input features or modalities；
- feature version；
- split strategy；
- model name；
- model hyperparameters；
- random seed；
- training parameters；
- evaluation metrics；
- output directory。

### 5.2 实验记录必须足以复核结论

探索性实验至少记录输入、关键参数、随机种子、命令、输出和指标。决策级与论文级实验进一步记录：

- code version note；
- command；
- config file；
- package versions；
- random seed；
- input data version；
- output path；
- metrics；
- runtime；
- hardware information。

### 5.3 Benchmark 必须公平

不同模型比较时必须尽可能保持一致：

- 使用相同 train / validation / test split；
- 使用相同输入信息；
- 使用相同评价指标；
- 使用相同预处理版本；
- 明确区分模型能力和特征工程能力。

如果某个模型使用额外数据或预训练权重，必须在结果表中明确标注。

### 5.4 验证必须分层，smoke 不等于科研证据

执行数据、模型或统计任务前，必须标记其证据层级：

1. **工程 smoke / dry-run**：使用能发现解析、接口、shape、依赖、日志和运行错误的最小输入。它只证明代码路径可运行。
2. **科研决策级实验**：达到能够比较方法或判断效应的最低有效规模，必须覆盖研究所需的异质性、split、独立重复和不确定性。
3. **论文级实验**：使用计划中的正式规模，并包含与 claim 对应的 seeds/replicates、严格 split、统计不确定性、稳健性分析和外部或正交验证。

规模规则：

- 用户或 `project_plan.md` 明确的最低有效规模具有最高优先级。例如至少 500 cells 才能分辨效应时，20 cells 只能用于工程 smoke；
- 不得用 smoke 结果排序模型、判断效应、否定假设、冻结科学结论或改变论文方向；
- 只有代码路径、输入契约、运行环境或失败模式发生实质变化时才需要新的 smoke；
- 已有 smoke 通过后应复用其证据并尽快扩大，不得连续生成多个低功效 pilot；
- 科研决策级规模应依据用户领域判断、计划书、预期效应、方差/power、样本异质性和 split 设计确定，而不是依据运行方便程度；
- 若正式扩大受到成本或数据 blocker 限制，应明确记录 blocker、解决条件和不能支持的结论，而不是用更小规模代替。

### 5.5 外部 API 和昂贵计算必须缓存

涉及外部 API、预训练模型服务或昂贵推理时：

- 调用前估算请求数量、运行时间、存储和费用；
- 缓存请求参数、模型版本、输入标识和返回结果；
- 支持断点恢复，避免失败后从头执行；
- 密钥、token 和 credential 不得写入代码、日志或 Markdown；
- 正式运行前先确认缓存复用和失败重试策略。

### 5.6 生信测量误差与弹性判据

DNA/RNA-seq、单细胞测量、ATAC-seq、Hi-C 和蛋白组等数据是受测序深度、稀疏性、dropout、batch、比对与定量、peak/contact calling、缺失值和动态范围影响的观测，不是无误差的生物学真值。

- 必须写清预测 target 是原始观测、处理后数值还是派生标签，并说明主要误差来源；
- 默认结论边界是“解释或预测当前 assay 与处理流程得到的观测”，不能直接写成恢复真实生物状态或证明机制；
- 不得脱离任务依据预设统一的 correlation、AUROC、accuracy 或其他绝对门槛；
- 有严格可比的同行 benchmark 时，优先在相同 dataset/cohort、split、输入信息、预处理和 metric 下比较。超过同行，或在不确定性范围内达到实际/统计非劣，可作为路线可行性的 GO；
- 与同行齐平不自动等于论文方法创新。若性能持平，必须另有新任务、泛化、效率、解释性、机制或生物学发现支撑论文贡献；
- 只有部分条件可比的文献数字只能作为背景范围，不能作为硬性 pass/fail；
- 新任务没有可比 benchmark 时，不设武断 SOTA 分数线。使用简单基线、null/permutation 或负对照、重复稳定性、不确定性区间、敏感性分析及生物学/正交一致性组成证据；
- 如果存在技术重复、split-half reliability、跨 assay concordance 或已知复现水平，应估计或讨论 measurement ceiling，并相对该上限解释模型表现；
- 噪声或样本不确定性使有用信号与失败无法区分时，应判为 INCONCLUSIVE。只有充分决策级证据排除了实际有用效应，或发现致命无效性时才判 STOP；
- 探索后可以调整判据，但必须记录调整原因，并用后续 held-out 或 confirmatory 分析验证，禁止事后移动阈值来制造 GO。

## 6. 模型开发规则

### 6.1 从强基线开始

任何复杂模型都必须和简单模型比较。根据领域选择合适基线，例如：

- mean / majority baseline；
- linear regression / logistic regression / ridge；
- random forest；
- XGBoost / LightGBM / CatBoost；
- shallow MLP；
- deep learning model；
- foundation model adapter。

如果复杂模型不能显著超过强基线，需要诚实报告，并分析原因。

### 6.2 模型接口统一

不同模型应尽量遵循统一接口：

```python
fit(train_data, valid_data, config)
predict(test_data)
evaluate(test_data)
save(path)
load(path)
```

模型内部可以不同，但外部训练、评价和保存方式应保持一致。

### 6.3 模型必须支持消融实验

涉及多特征、多模态或多组件贡献的核心模型，必须支持 ablation。不能做消融的模型，不适合作为核心结论唯一依据。

### 6.4 模型必须关注可解释性

本项目不是纯 prediction leaderboard。模型必须尽量回答“为什么”。

根据模型类型，至少支持一种解释方式：

- feature importance；
- SHAP；
- permutation importance；
- modality / feature family contribution；
- integrated gradients；
- attention attribution；
- graph explanation；
- in-silico deletion / perturbation。

## 7. 统计学与科学解释规则

### 7.1 不只报告整体平均值

所有核心结果都应根据领域做分层分析，例如：

- by sample / cell type / cohort / condition；
- by time point / phase / batch；
- by target class / gene class / feature class；
- by expression level or difficulty group；
- by biologically meaningful subgroup。

### 7.2 统计结论要有不确定性估计

重要结论不能只给一个点估计。应尽量报告：

- confidence interval；
- standard error；
- bootstrap result；
- multiple-testing correction；
- effect size；
- statistical significance；
- biological or domain significance。

### 7.3 科学解释优先于模型炫技

模型复杂度不是目标。每个关键模型结果都应尽量转化为领域表述：

- 哪些信息最重要；
- 哪类样本或目标最依赖这些信息；
- 哪些结果与已有知识一致；
- 哪些结果提出了新的可验证假设；
- 哪些负结果说明了真实上限。

## 8. 结果与论文规则

### 8.1 图表要服务主线

所有图表都应围绕项目主线，而不是堆叠漂亮但无关的结果。

### 8.2 结果必须可追溯

论文或报告中的每个数字、每张图、每个表格都应能追溯到：

- 原始数据；
- 处理脚本；
- 配置文件；
- 模型版本；
- 结果文件；
- 作图脚本。

### 8.3 负结果也要保留

如果某个模型没有提升，或某类信息贡献很小，也应记录。负结果对严肃科研项目很重要。

## 9. 文档规则

### 9.1 进入稳定使用的核心模块必须有说明

至少需要说明：

- 模块目的；
- 输入格式；
- 输出格式；
- 主要函数或类；
- 使用示例；
- 常见问题。

### 9.2 README 要面向新加入者

README 应帮助新加入项目的人快速理解：

- 项目目标；
- 数据来源；
- 环境安装；
- 如何运行最小 pipeline；
- 如何复现实验；
- 如何新增模型；
- 如何新增数据集或任务。

### 9.3 重要设计需要记录

关键技术选择应写入设计文档，而不是只存在聊天记录或个人记忆中。

### 9.4 Markdown 文档默认中文

后续新生成的说明类 Markdown 文档默认使用中文撰写，尤其是：

- README；
- 方法说明；
- runbook；
- 项目总结；
- prompt / result 记录；
- 设计文档；
- 排错说明；
- 实验报告。

代码标识、命令、配置键、字段名、文件路径、模型名称、指标名称、包名和标准英文技术术语可以保留英文，避免强行翻译降低准确性。

只有在用户明确要求英文、目标期刊/合作者需要英文、或必须保留英文原文对照时，才生成英文说明文档。

### 9.5 长期项目保持轻量证据索引

默认只使用根目录 `paper_map.md` 连接 claim、决定性实验、当前证据、状态、目标图表和缺失证据，不建立多个 registry。日常过程保留在紧凑的 prompt/result 中；只有历史过长影响上下文时才生成一个阶段 checkpoint。

## 10. 代码质量规则

### 10.1 Python 代码规范

对获得 GO、需要复用或准备进入 paper-grade 的代码推荐遵循：

- Python 3.11+；
- type hints；
- dataclass / pydantic 用于结构化配置；
- pathlib 处理路径；
- logging 记录日志；
- pytest 编写测试；
- ruff / black 做格式化和静态检查。

### 10.2 函数和类设计

稳定代码中的函数应该短而清楚。探索性纵向切片允许一个脚本串起完整流程，只要步骤清晰且结果可复核；路线保留后再拆分。稳定代码避免：

- 函数内部写死路径；
- 函数内部偷偷读取全局变量；
- 训练逻辑和画图逻辑混在一起；
- 数据清洗和模型训练混在一起。

### 10.3 错误处理

错误信息必须帮助定位问题。例如，不要只抛出：

```text
File not found
```

而应说明：

```text
Expected processed expression matrix at <path>. Please run `prepare_expression_matrix` first.
```

### 10.4 运行日志与进度反馈

长时间运行的决策级或论文级脚本必须提供阶段进度；短探索脚本不要求建设完整日志系统。

基本要求：

- 命令行脚本应支持 `--log-level` 参数；
- Python 脚本应使用标准库 `logging`；
- 日志至少记录输入文件、输出文件、关键配置参数、数据规模、主要处理阶段、耗时阶段和完成状态；
- 长循环应按 sample、cell、chromosome、batch、chunk 或领域内自然单位给出阶段性进度；
- 日志不应泄露敏感信息，也不应刷屏。

## 11. 变更兼容性

修改核心流程时，应确认：

- 旧配置是否还能运行；
- 旧结果是否还能解释；
- 是否需要 bump data / feature / model version；
- 是否需要更新文档。

## 12. 开发优先级

项目开发按论文关键路径排序，而不是按固定的工程成熟度清单排序：

1. 明确核心科学问题、candidate claims、决定性比较和证据阈值；
2. 做足以定义有效 target、split、metric 和输入的数据检查，只解除决定性比较的真实 blocker；
3. 在最早可行的科研周期同时设计简单基线和有竞争力的候选模型，并在最低有效规模上运行比较；
4. 根据结果立即给出 GO、PIVOT、STOP 或 INCONCLUSIVE，不因已有代码投入继续深挖；
5. 对 GO 的 claim 补充严格 split、不确定性、消融、对照、重复、外部验证和机制解释；
6. 完成 claim-to-figure 故事，并只对最终证据依赖的流程做复现加固、模块化、文档化和交付整理。

不得因为仓库尚未达到想象中的“工程完美”而长期推迟有科研信息量的实验。

## 13. 工作态度

本项目要按照正式科研项目推进：

- 不追求表面跑通；
- 不为了漂亮结果牺牲严谨性；
- 不用复杂模型掩盖数据问题；
- 不把 benchmark 写成不可复现的脚本；
- 不把临时结论当最终结论；
- 不忽视负结果；
- 不忽视统计学和领域解释。

最终交付物应该经得起以下检查：

- 换一个人能否复现；
- 换一个数据集能否扩展；
- 换一个模型能否接入；
- 审稿人能否相信；
- 领域专家能否理解；
- 后续论文或项目能否继续发展。

## 14. 对 AI/开发代理的要求

后续任何 AI 或开发者参与本项目时，必须遵循：

1. 先理解项目目标，再写代码。
2. 先阅读已有结构和规则，再新增模块。
3. 优先复用已有接口；但不得为了接口统一推迟首次有效模型实验。
4. 探索阶段优先可追踪和快速决策，获得 GO 后再要求可测试、可扩展和长期复用。
5. notebook 或单脚本可用于探索和首次比较；进入重复使用或论文级后再迁移核心逻辑。
6. 不写硬编码路径。
7. 不随意引入重依赖。
8. 不为了假设性的长期需求提前全面工程化，也不为短期跑通牺牲结论有效性。
9. 修改公共接口时必须同步更新文档和调用方。
10. 每次完成工作都应说明改了什么、如何验证、还有什么风险。

### 14.1 Prompt / Result 内稿质量门

- 正式 `promptN.md` 和 `resultN.md` 不得直接使用第一稿；
- 先在工作上下文形成未发布内稿，至少分别进行科学审查和可执行性/事实审查；
- 发现会改变比较、规模、判据、决策、Claim 边界或执行结果的问题后必须修改并重新审查；
- 只有未发现实质问题时才生成单一正式文件并更新状态；
- 无法消除的关键歧义必须阻止发布，并明确请求用户确认；
- 内稿不作为额外文件、registry 或历史记录保存，通常 2-3 次聚焦检查即可，不进行无意义的文字润色循环。

### 14.2 AI 代理的低 token 上下文规则

为避免大型数据文件、日志和重复读取造成无意义的上下文消耗，AI 代理默认采用低 token 工作模式。节省 token 不能降低工程质量、验证强度或科研严谨性。

必须遵循：

1. 搜索优先于整文件读取。先用 `rg -n` 定位关键词、函数、配置项或标题，再读取必要的局部片段。
2. 大文件默认只读取有界片段。优先使用文件头、文件尾或指定行段，不直接展开完整长文档、manifest、TSV、JSON、日志或生成结果。
3. 大型结构化数据默认程序化摘要。优先统计行数、列数、唯一值数量、缺失率、重复键、文件大小和少量示例行，不把大量原始记录送入上下文。
4. 日志默认检查错误和尾部。优先搜索 `ERROR`、`WARNING`、`Traceback`，并读取有限的尾部内容；只有诊断需要时才扩大范围。
5. 变更检查只查看与当前任务相关的目标文件或局部 diff，不展开无关改动。
6. 不重复搬运已确认的信息。优先复用已有 summary、result、readiness、runbook 或 checkpoint 文档。
7. 对 IDE 自动附带的大型选区保持克制。除非当前任务确实依赖原始内容，否则把它视为背景引用，不复述、不整体分析、不再次载入。
8. 中间汇报只保留关键节点。说明当前阶段、重要发现、阻塞和验证结论。
9. 长任务必须将详细输出写入日志文件，终端和对话中只保留阶段进度、关键统计和最终摘要。
10. 当局部信息不足以保证正确性时，必须扩大读取范围，并简要说明扩大范围的原因。

低 token 模式不是跳过必要审计、测试或验证的理由。
