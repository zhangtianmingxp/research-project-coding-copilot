# Interactive Research Workflow Rules

本文件定义 Codex / Claude Code 在科研项目中逐轮推进工作的规则。

## 1. 项目定位

这是一个交互式科研项目推进模板，不是全自动 agent。

AI 的职责是：

- 阅读 `project_plan.md`、`PROJECT_RULES.md` 相关章节和项目规则。
- 在用户要求时生成 `ans_qes/promptn.md`。
- 在用户输入“执行当前轮”或指定某个 prompt 后执行该轮。
- 执行后生成 `ans_qes/resultn.md`。
- 每个阶段完成后停止，等待用户下一条明确指令。

AI 不得：

- 自动生成下一轮 prompt。
- 自动执行刚生成的 prompt。
- 调用远程 LLM API。
- 在用户未确认时覆盖已有 `resultn.md`。

例外：如果用户明确要求“继续 N 轮”或“从当前 result 继续执行 N 轮”，允许进入受限连续推进模式。该模式最多执行用户指定的 N 轮，不能无限循环，遇到测试失败、不确定下一步、大文件/密钥风险、数据泄漏风险或需要破坏性操作时必须停止。

### 1.1 短指令协议

用户不需要在每次操作后重复说明“不要执行”或“不要生成下一轮”。以下短指令具有固定边界：

| 指令 | 固定行为 |
| --- | --- |
| `初始化` | 只安装项目模板，然后停止 |
| `接管项目` | 识别并接管已有项目，保留项目自有文件，然后停止 |
| `生成项目计划书：...` | 根据用户研究想法生成或完善 `project_plan.md`，然后等待审查 |
| `整理项目计划书：...` | 结合已有仓库内容和用户理解整理计划书，然后等待审查 |
| `项目组合审计：<目录...>` | 只读审计指定目录内全部项目族，分类为 WRITE_NOW / ONE_DECISIVE_EXPERIMENT / HOLD / STOP |
| `成果收割审计` | 对当前项目族及可识别相邻版本执行同一只读分类 |
| `新版本审计` | 先做成果收割 Gate；仅对 ONE_DECISIVE_EXPERIMENT 审计前序 blocker，不创建新版本、计划书或 prompt |
| `项目体检` | 只读检查项目状态和风险 |
| `状态` | 报告当前轮次、阶段和下一步 |
| `快速验证：...` | 围绕一个 claim 和一个决定性比较生成首轮紧凑 prompt，最多使用 1-3 轮 |
| `继续快速验证` | 仅在上一轮为 INCONCLUSIVE 且未满 3 轮时生成下一轮紧凑 prompt |
| `生成下一轮` / `下一轮` | 只生成下一轮 prompt，然后停止 |
| `执行当前轮` | 执行当前 prompt，验证并生成同轮 result，然后停止 |
| `继续 N 轮` | 最多连续生成并执行 N 轮，然后停止 |

短指令本身就是对应动作的用户授权，不得要求用户重复确认同一个动作。只有目标不明确、缺少必要信息或触发工具权限边界时才询问。

## 2. 每轮状态机

每轮只能处于以下状态之一：

```text
idle
prompt_drafted
prompt_approved
executed
result_reviewed
```

允许的转换：

```text
idle -> prompt_drafted
prompt_drafted -> prompt_drafted
prompt_drafted -> prompt_approved
prompt_approved -> executed
executed -> executed
executed -> result_reviewed
result_reviewed -> prompt_drafted
```

禁止自动执行 `result_reviewed -> prompt_drafted`。必须由用户明确要求生成下一轮 prompt。

如果用户明确要求受限连续推进 N 轮，可以在同一轮用户指令下重复执行：

```text
prompt_drafted -> prompt_approved -> executed
```

但总轮数不得超过 N，且每轮必须保留 `promptn.md` 和 `resultn.md`。

## 2.1 项目计划书前置规则

`project_plan.md` 是正式轮次的必要输入。初始化只安装模板，不代表研究计划已经完成。

新项目可以由用户自行填写，也可以由 AI 根据用户提供的研究问题、已有数据、预期方法、限制条件和最终论文或软件目标生成初稿。

已有项目可以结合仓库中的 README、docs、配置、源码结构、checkpoint 和最近结果，以及用户对项目现状和未来方向的理解，整理或更新计划书。必须区分：

- 已经实现的内容；
- 已验证的结果；
- 用户提供的理解或判断；
- AI 明确标注的假设；
- 尚未执行的未来计划。

不得仅根据文件名推断科学结论。计划书仍含模板占位内容或信息明显不足时，不得生成正式 `promptn.md`；应先请用户完善，或协助生成计划书并等待审查。

建立或整理后继版本计划前，先执行项目组合与成果收割 Gate。对明确范围内的项目族去重后各定义一个最小可发表单元，并只给 `WRITE_NOW / ONE_DECISIVE_EXPERIMENT / HOLD / STOP` 之一。WRITE_NOW 冻结新实验并进入投稿，HOLD 与 STOP 不再生成 prompt 或新版本；只有 ONE_DECISIVE_EXPERIMENT 可以继续，而且只允许执行一个能改变投稿判断的实验。四类标签是资源动作，不替代单轮 GO/PIVOT/STOP/INCONCLUSIVE，默认不另建文件或 registry。

若当前仓库属于复用同一数据/outcome 的版本项目族，并且 Gate 为 ONE_DECISIVE_EXPERIMENT，建立或整理后继版本计划前还必须有界审计前序终局 result、checkpoint、计划书摘要和 `paper_map.md`。提取根本 blocker，并说明新版本引入了什么新数据、独立样本、测量分辨率、estimand、正交证据或独立先验假设。仅改模型、表示、阈值、seed、metric、亚组或版本号不构成重启理由；实验应优先在当前仓库完成。

同一 blocker 已导致两个版本 STOP，或同一数据/outcome 项目族已连续三个版本 STOP 时，先执行项目族审计。只有 GO 才能创建后继版本；PIVOT、STOP 或 INCONCLUSIVE 时停止，不得生成新计划或 prompt。STOP 后最多允许一次诊断性失败归因，不得递归做 post-hoc 挽救。

计划书只详细展开当前活动 Gate，后续未解锁 Gate 各用一句话记录。约 300 个非空行或 20 KB 仅作为范围提醒；已有长计划默认只读取当前活动 Gate 及必要全局章节。

## 3. 生成 promptn.md 的规则

触发条件：用户输入“生成下一轮”“下一轮”或明确指定某轮 prompt。

操作要求：

1. 读取 `project_plan.md` 的当前活动 Gate 和必要全局章节；若最新结果为 STOP，不得为同一 claim 继续生成 prompt，也不得未经项目族 GO 静默启动新版本。
2. 用 `rg` 定位并读取 `PROJECT_RULES.md` 中与本轮任务相关的章节。
3. 读取 `.research_agent/project_state.md` 和 `.research_agent/progress.json`。
4. 检查 `ans_qes/` 中已有 prompt/result 编号。
5. 明确本轮推进的论文核心 claim、关键不确定性、目标 figure/table 或具体 blocker。
6. 在数据、基线、候选模型、实验、分析和工程候选行动之间比较论文信息增益，不默认延续上一轮最深的子问题。
7. 一旦数据足以定义有效 target、split 和 metric，优先生成“简单基线 + 有竞争力候选模型 + 决策级比较”的最短纵向切片。
8. 将实验标记为工程 smoke、科研决策级或论文级，并写明数据规模、独立样本单位、规模依据和升级/停止标准。
9. 工程 blocker 最多先安排一次聚焦修复；若仍失败，应评估绕过、简化、换实现或判为 INCONCLUSIVE。不得连续两轮只做工程补强。
10. 先在当前工作上下文生成未发布内稿，不写入 `ans_qes/`，也不更新状态。至少分别进行一次科学审查和一次可执行性/编辑审查，发现实质问题后修改并重新检查。
11. 只有未发现实质问题时，才把审定内容一次性写入指定或下一个编号的 `ans_qes/promptn.md`，运行严格结构检查并更新状态为 `prompt_drafted`，然后停止等待用户审查。

生成 prompt 时不得修改科研代码，不得生成 `resultn.md`。

Prompt 只保留：`科学决策`、`最小充分工作`、`实验层级与规模`、`判据`、`产物`。全局规则不得重复写入每轮 prompt。

## 4. 执行 promptn.md 的规则

触发条件：用户输入“执行当前轮”或明确指定某个 prompt。

操作要求：

1. 读取对应 `ans_qes/promptn.md`。
2. 读取 `PROJECT_RULES.md` 中与本轮任务相关的章节。
3. 按 prompt 执行本轮任务。
4. 走通从输入到模型/分析再到结果的最短路径。仅运行能够发现数据无效、泄漏、指标错误、代码路径失败或核心结论错误的检查。
5. 先生成未发布 result 内稿。至少进行科学证据审查和事实/产物审查：确认完成内容真实、指标有产物支撑、负结果未遗漏、决策符合预设判据、同行比较可比、Claim 没有越过 assay 观测边界。
6. 修改内稿并重复检查，直到未发现实质问题；若关键歧义无法消除，则不生成正式 result，报告具体 blocker。
7. 只有审查通过后才写入或更新同编号 `ans_qes/resultn.md`，运行严格结构检查并更新状态为 `executed`。
8. 停止并等待用户审查。

若本轮决定为 STOP，应把 claim 的根本 blocker 和重新开放所需的新证据写入现有 `paper_map.md`，然后结束该 claim/版本。除用户明确要求一次诊断性失败归因外，不得继续生成挽救性 prompt。

如果 `resultn.md` 已存在，除非用户明确要求覆盖或更新，否则不得直接覆盖。

Result 只保留：`完成内容`、`关键证据`、`决策`、`Claim 边界`、`产物与命令`、`下一项最高价值工作`。`决策` 必须是 GO、PIVOT、STOP 或 INCONCLUSIVE。

内稿是临时工作材料，不建立 `prompt*_draft.md`、`result*_draft.md` 或审稿 registry，不向用户输出详细内部推理。通常 2-3 次聚焦检查足够，不为不影响执行和解释的措辞无限迭代。

## 4.1 快速验证模式

- 一个快速验证只处理一个 claim、一个决定性比较和一个最小决策级规模。
- 最多使用 1-3 轮；GO、PIVOT 或 STOP 立即结束。
- INCONCLUSIVE 必须指出唯一关键缺失证据；未满 3 轮时用户可要求“继续快速验证”。
- 第 3 轮后无论结果如何都停止。
- 不建立快速验证 registry 或额外状态文件。
- 只有出现决策级结果、claim 改变、准备升级到 paper-grade 或开始写论文时才更新根目录 `paper_map.md`。
- 每个 prompt/result 都必须先通过未发布内稿质量门；内稿复查次数不计入科研轮次。

## 5. 受限连续推进 N 轮

触发条件：用户明确要求继续固定轮数，例如“从 result5.md 继续执行 3 轮”。

操作要求：

1. 先运行 context summary 和编号检查。
2. 从下一个可用编号开始。
3. 每轮都必须生成 `promptn.md`、执行、生成 `resultn.md`、运行检查并更新状态。
   每个正式 prompt/result 写入前都要单独通过未发布内稿质量门，内稿复查不计入 N。
4. 完成 N 轮后必须停止。
5. 遇到以下情况必须提前停止：
   - 测试或检查失败且不能局部修复；
   - 下一步科研或工程判断不确定；
   - 出现大文件、模型权重、密钥、数据泄漏或 benchmark 不公平风险；
   - 需要外部凭据或破坏性操作；
   - 需要读取过宽上下文才能继续。
   - 当前 claim/版本已 STOP，或继续需要未经项目族 GO 的后继版本。

## 6. 科研项目质量原则

- 必须遵守 `PROJECT_RULES.md`。
- 论文核心问题和证据链优先于工程完整度；工程工作必须服务于可信结果或解除明确 blocker。
- 默认按“尽早模型、尽早实验、尽早决断”推进。代码成熟度必须跟随证据成熟度：探索路线允许清晰、可追踪的脚本或 notebook；获得 GO 并准备升级后再补模块化、通用接口、广泛测试和完整文档。
- 不把未完成的子任务自动当作下一轮。每轮结束后重新比较所有主线候选行动，选择单位时间内最可能改变论文判断的一项。
- 不把版本号当作新证据。复用同一数据/outcome 的路线必须继承前序根本 blocker；重复 STOP 后按项目族止损，除非独立新信息真正改变可识别性。
- 计划书只详细描述当前 Gate，不提前展开未解锁的长任务树。
- 非阻断问题只做一句记录。一个工程 blocker 聚焦修复一次后仍未解决，优先绕过、简化或换路线；只有它会使核心证据失效且无替代方案时才继续深入。
- 微型规模只能在适用时验证代码路径。若用户或计划书规定至少 500 cells 才能分辨效应，必须以 500 cells 作为科研推断下限。
- 已通过的 smoke 不重复做；不得用低功效结果排序模型、否定假设、冻结科学结论或改变论文方向。
- DNA/RNA-seq、单细胞、ATAC、Hi-C、蛋白组等观测默认含 assay 与处理误差。必须区分测得的 target 和未观测的真实生物状态，不能把预测观测值直接写成恢复生物学真值。
- 判据优先采用相对且带不确定性的标准。有严格匹配同行 benchmark 时，超过或达到实际/统计非劣即可支持路线可行；仅持平时还需其他论文贡献。没有可比 benchmark 的新任务使用简单基线、null/负对照、重复稳定性、不确定性和生物学/正交一致性，不强设绝对分数线。
- 噪声过大导致无法区分有效信号与失败时判为 INCONCLUSIVE，不因未达到武断阈值直接 STOP；探索后调整判据必须记录并在 held-out/confirmatory 分析中复核。
- 遇到问题先判断它是否会改变数据、指标、统计推断、核心图表或关键结果复现。不会影响主线的偶发/外观问题只记录，不为其反复实验或单独占用 round。
- 不把研究项目当 demo。
- 探索性脚本可以用于尽快完成首次有效比较；只有进入重复使用或 paper-grade 的核心流程才要求沉淀和清晰模块边界。
- 避免数据泄漏，尤其是 benchmark、split 和外部验证。
- 长任务应有日志或进度输出。
- 结果应可追踪到代码版本说明、配置、命令和数据版本。
- 文档默认中文，代码标识、文件路径、指标名和模型名保留英文。

## 7. 上下文预算规则

默认使用低上下文模式。项目变大后，AI 不得把计划书、日志、结果表、notebook、manifest、旧 result 文件和长 diff 一股脑读进上下文。

推荐顺序：

1. 先运行仓库摘要命令，例如 skill 级 `context-summary` 或本地 `scripts/research_flow.py status` / `check`。
2. 使用 `rg -n` 定位相关标题、函数、配置键、错误信息或文件路径。
3. 只读取与当前任务相关的最小片段。
4. 不默认读取完整日志；失败时优先看 stderr，再搜索日志中的 `ERROR`、`WARNING`、`Traceback` 或阶段名。
5. 不默认读取完整 TSV/CSV/JSON/manifest/notebook/result table；应先总结文件大小、行列数、列名、缺失值、唯一键和少量目标行。
6. 不重复读取大量旧 `ans_qes/result*.md`；优先读取最近 1-3 个相关 result，或使用摘要。
7. 如果必须扩大读取范围，先说明原因，再逐步扩大。

低上下文模式不是降低质量；必要的测试、数据泄漏检查、复现性检查和科学验证仍必须执行。
